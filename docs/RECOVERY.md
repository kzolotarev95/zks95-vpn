# Восстановление после неудачного обновления

Не удаляйте Docker volumes и не выполняйте автоматический downgrade базы. В новой версии схема может стать несовместимой со старым приложением. Скрипт update сообщает предыдущий commit и сохраняет PostgreSQL dump и `.env` перед изменениями.

1. Остановите nginx, web и api через Compose с сохранённым режимом. PostgreSQL оставьте запущенным.
2. Сделайте отдельную копию текущей повреждённой БД, `.env`, старых backups и логов для диагностики. Новые данные после backup при восстановлении будут потеряны; прежде определите нужную точку восстановления.
3. Создайте отдельный checkout нужного предыдущего commit. Скопируйте туда сохранённый `.env` и `.deployment-mode` с правами 600. Не используйте `git reset --hard` в рабочем checkout.
4. Проверьте backup: `pg_restore --list backups/НУЖНАЯ-КОПИЯ.dump`. Желательно сначала восстановить его в отдельный тестовый PostgreSQL.
5. После выбора backup восстановите БД. Для development команда ниже очищает существующие таблицы, production требует дополнительного `-f docker-compose.prod.yml`:

```bash
docker compose exec -T postgres pg_restore -U zks95 -d zks95 --clean --if-exists --no-owner --exit-on-error < backups/НУЖНАЯ-КОПИЯ.dump
```

6. Соберите предыдущий код и запустите приложение с тем же Compose project name `zks95-vpn`, затем выполните health-check и проверку входа / заказов. Не запускайте миграции новой версии над восстановленной базой до выяснения причины сбоя.

Этот план требует репетиции на отдельной VPS перед эксплуатацией. Point-in-time recovery, offsite storage и автоматический rollback ещё не реализованы.
